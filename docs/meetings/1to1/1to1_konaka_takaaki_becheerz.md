### 4. 次廣共有トーク — tugilo-os（きっかけ・目的）

#### 4.1 一言で言うと

> 一人会社の **司令部** を Git に置いた。実装コード置き場ではなく、全案件の SSOT・判断・証跡・タスクを Claude Code で統括するためのリポジトリ。

#### 4.2 思い立ったきっかけ

1. **案件が増え、会話が正になりかけた**  
   Religo（dragonfly）や顧客案件を Cursor 中心で回すうち、「チャットで話したはず」「どこまで決めたか」が散らばり始めた。
2. **AIを増やすほど、統括が必要になった**  
   Cursor で実装は速くなるが、優先順位・Decision・本番境界・横断影響を会話履歴に頼ると再現できない。
3. **小中さんの Claude Code 実践が刺さった**  
   スリーバイス（2026-05-19）で共有された「手順書（スキル）で再現する」「一度教えたことを忘れない」運用が、自分の課題（属人チャット依存）と重なった。
4. **「人を増やす前に構造を変える」を自分に適用した**  
   外向けの業務改善と同じ思想を、自社の開発運用にも当てはめた結果が tugilo-os。
5. **端末をまたいでも「続き」が切れないようにしたかった**  
   別端末で作業したあと、チャット履歴やローカルメモに依存すると再開コストが高い。  
   **GitHub でコードを同期**しつつ、**判断・手順・差分の文脈は tugilo-os 側のドキュメント／SSOT で持つ**形にすれば、どこからでも同じ続きができる。

#### 4.3 目的

| 目的 | 具体 |
|------|------|
| **全プロジェクトを一箇所で把握** | 状況・優先度・依存を司令部に集約 |
| **会話ではなく構造化データを正にする** | Decision / Evidence / Task を Git 管理 |
| **端末をまたいでも作業を続けやすくする** | 各PJは GitHub で最新コードを保ち、文脈・差分・次アクションは tugilo-os で同期 |
| **Claude Code を唯一の統括ハブにする** | AI同士の雑談運用を中心にしない |
| **実装は各プロジェクトに残す** | Religo 等は従来どおり各 repo＋Docker＋Cursor |
| **人間が最終責任** | 本番・main・契約・金銭は人間承認必須 |

#### 4.3.1 なぜ GitHub 同期＋tugilo-os ドキュメント管理か（続けやすさ）

一人会社でも、作業場所は Mac mini 母艦・ノート・外出先など **端末が分かれる**。ここで壊れやすいのはコードそのものより、「前回どこまでやって、次に何をするか」の **文脈**。

| 層 | 何を同期するか | 手段 | 効果 |
|----|----------------|------|------|
| **実装層** | 各プロジェクトのソース・設定（SECRET除く） | 各 repo → **GitHub**（pull/push） | どの端末でも **最新コード** から再開できる |
| **司令部層** | 判断・Task・Evidence・Handoff・運用ドキュメントの差分 | **tugilo-os** 自体も Git（方針: GitHub Private） | 「なぜそうしたか」「いま何が未完か」がチャットに残らない |
| **バックアップ** | SSD 障害・端末故障への備え | Time Machine ＋ GitHub（DEC-20260719-002） | 単一障害点を減らす |

**当日用の説明例**

> 別の端末で触ったあとも、GitHub でコードを最新に保てる。それだけだと「ファイルは新しいが、頭の中の続き」が消える。なので tugilo-os 側で Decision や Task、ドキュメント差分まで Git 管理して、**続きの作業がどこからでも同じ手順で再開できる**ようにしている。

**小中さん向けの対比（刺さりどころ）**

- Claude Code の「スキル／手順の再現」＝ **やり方の記憶**
- tugilo-os の Git／Evidence＝ **判断と進捗の記憶**
- 両方あると、端末・セッション・人が変わっても作業が切れにくい

#### 4.4 構成（三層）

```text
人間（方向・最終責任・本番）

Claude Code（統括ハブ：整理・Task分解・指示・証跡確認）
```

#### 4.9 管理プロジェクトの追加の仕方（現行ルール）

**権限の正（DEC-20260722-001）**

| 概念 | 何で決まるか | 役割 |
|------|----------------|------|
| **管理対象（書き込み可）** | `tugilo-os.code-workspace` の `folders` に入っているか | Claude Code が Task/Handoff 範囲内で直接触れる |
| **台帳** | `data/projects/<id>.yaml` | tech_stack・lifecycle・path 等のメタ情報。**権限判定の前提ではない** |

台帳が無くても workspace に入っていれば管理対象。未登録なら Claude Code は台帳登録を **提案** するだけ。

**追加手順（最短）**

1. **人間:** Cursor で `tugilo-os.code-workspace` を開き、`folders` にプロジェクトパスを追加する。  
   → これで「管理対象」になる。
2. **推奨:** `templates/project.yaml` を `data/projects/proj_xxx.yaml` にコピーし、識別子・表示名・local_path・tech_stack・`lifecycle_stage`（PROPOSAL / DEVELOPMENT / MAINTENANCE）を埋める。SECRET（`.env`・鍵）は書かない。
3. **任意:** 低リスクの現状調査 Task を切る。Evidence を残す。
4. **実装時:** Task/Handoff で「どのプロジェクトの・どの範囲か」を明示してから触る。

**外すとき**

- workspace の `folders` から外す → 管理対象外。
- `data/projects/` の YAML は削除せず `status: PAUSED` 等で履歴を残す。

**やってはいけないこと**

- シンボリックリンクの自動作成、`.env` の取り込み、本番情報の SSOT 記載
- Task/Handoff なしの横断書き込み、複数案件の同時変更

#### Religo（1to1・リファーラル支援）デモとフィードバック

- リファーラル提案: 履歴から「誰と誰が合うか」を AI 提案。
