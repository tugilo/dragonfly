> 今日はまず、いま実際にどこで困っているかを教えていただきたいです。  
> そのうえで、全部をいきなり作り替えるのではなく、Google Workspace や GAS を使って、今の運用を活かしたまま小さく効率化できる部分があるかもしれません。  
> いくつか例を持ってきたので、近いものがあるか見ながらお話しできればと思っています。

#### Google Workspace / GAS 活用例（話題提供）

**1. Oracle / Excel の集計結果を Google スプレッドシートに自動反映**

- **現状イメージ:** Excel で ODBC 接続し、手作業で加工・集計している。
- **例:** 毎日・毎週決まったタイミングで CSV 出力 → Google スプレッドシートに取り込み → 集計表を自動更新。
- **効果:** 確認用の表を毎回作り直さなくてよくなり、社内共有もしやすくなる。
- **確認したいこと:** 今、Excel で毎回作っている表・一覧・集計は何か。

**2. 案件・調査・製本工程の進捗管理表を Google スプレッドシート化**

- **現状イメージ:** 案件・調査・製本工程の状態が、個別 Excel、口頭確認、担当者の記憶に散らばっている。
- **例:** 案件ごとに「受付中／調査中／確認待ち／制作中／納品済み」などを一覧化。
- **効果:** 誰が見ても、今どこで止まっているか分かる。
- **確認したいこと:** 「あの案件どうなっている？」と確認が発生しやすい業務はどこか。

**3. Google フォームで社内依頼・確認事項を受ける**

- **現状イメージ:** メール、口頭、LINE、紙などで依頼や修正指示が散らばる。
- **例:** 製本依頼、調査依頼、修正依頼、確認事項を Google フォーム入力にし、回答をスプレッドシートに蓄積。
- **効果:** 依頼内容の抜け漏れを減らし、後から検索できる。
- **確認したいこと:** 依頼内容が散らばって困っている業務はあるか。

**4. GAS で期限・確認漏れを自動通知**

- **現状イメージ:** 担当者が覚えている、または手作業で追いかけている。
- **例:** 「3日以上未対応」「納期前日」「確認待ち」の案件をメールや Google Chat に通知。
- **効果:** 催促・確認・抜け漏れチェックの手間を減らせる。
- **確認したいこと:** 納期前・確認待ち・未対応で、毎回人が見に行っているものは何か。

**5. 顧客ごとの Google Drive フォルダを自動作成**

- **現状イメージ:** 資料の保存場所やファイル名が人によって違い、探す時間が発生する。
- **例:** 新規案件登録時に、顧客名・案件番号付きフォルダを自動作成し、テンプレ資料も配置。
- **効果:** 資料の置き場所が統一され、引き継ぎや確認が楽になる。
- **確認したいこと:** 顧客資料・調査資料・成果物の保存ルールは統一されているか。

**6. 家系図・ルーツ調査の調査メモ管理**

- **現状イメージ:** 戸籍、文献、調査メモ、成果物、顧客対応履歴が分散しやすい。
- **例:** 顧客ごとに調査ステータス、参照文献、確認事項、成果物リンクをまとめる。
- **効果:** 過去案件を再利用しやすくなり、調査ノウハウが社内資産化する。
- **確認したいこと:** 過去の調査記録・文献メモ・成果物テンプレを再利用できる状態になっているか。

#### 今日の着地点

Google Workspace / GAS で全部を解決するのではなく、次の3分類に整理する。

1. **GASで小さく改善できるもの**
2. **既存 Oracle を活かして連携した方がいいもの**
3. **Web化・クラウド化まで考えた方がいいもの**

**締めトーク案**

> Google Workspace や GAS で全部を解決するというより、まずは「今の業務を変えずに、手作業・確認・転記を少し減らせる場所」を探すイメージです。  
> 今日お聞きした内容から、GASで小さく改善できるもの、既存 Oracle を活かして連携した方がいいもの、Web化・クラウド化まで考えた方がいいものに分けて整理できればと思っています。

- 次廣は、既存 VB システムに直接手を加えず、新たな Web インターフェースを社内サーバー上に構築し、PDF注文書を解析して Oracle DB に登録する改善案を提示。

**決定事項・合意内容**

- **PDF自動入力の実現方針:** 既存 VB システムには手を加えず、新しい Web ベースの入力画面を作る。PDF注文書をアップロードし、解析結果を確認・修正してから Oracle DB に書き込む。
- **システム構成（合意）:** 既存 Windows サーバーの **Hyper-V** 上に Linux ベースの Web サーバーを構築し、**社内ローカルで展開**。社内ネットワーク（Wi-Fi / 有線）経由でアクセス。社外からは既存 **VPN** を利用。外部インターネット公開はしない。
- **Google Workspace / GAS 案は不採用:** 外部アクセスやセキュリティリスクを理由に、Google Workspace / GAS を主軸とする案は取らない。**社内完結型 Web** を優先する。
- **段階的な実装:** 第一段階は最も負担の大きい **PDF入力自動化**。第二段階で日報などの Excel 帳票の Web化、多端末対応を検討する。
- **得意先直接入力:** 将来的には得意先向けの直接入力システム提供も可能性として認識。ただし初期スコープには入れない。

**現状の課題**

- **手入力の負担:** 事務員が月間300〜400件（大口顧客のみ）、全体ではその倍近い件数の PDF 注文書を手作業で入力している。
- **システム構成:** 三菱関連会社が開発した VB + Oracle の基幹システムが稼働中。
- **データ構造:** ヘッダーとフッターが 1:N の関係。本のパーツごと（表紙、本文、カバー等）に銘柄やメーカーを選択する必要がある。
- **注文書フォーマット:** 出版社ごとに注文書フォーマットが異なる。PC作成データだけでなく、手書きのものも存在する。
- **既存改善:** ODBC 経由で Oracle からデータを読み出し、日報作成・分析・伝票出力に活用している。

**提案された解決策**

- **PDF自動入力システム:** 大口顧客の PC 作成 PDF 注文書から優先的に自動化する。手書きは初期対象外または後回し。
- **入力画面:** ブラウザ上で PDF をドラッグ&ドロップし、解析結果を画面上で確認・修正してから登録する。
- **DB連携:** Oracle のテーブル定義書を参照し、キー項目、英字項目名、画面項目との対応、シーケンス番号、トリガーに配慮した書き込みロジックを設計する。
- **サーバー環境:** Windows サーバー上の Hyper-V に Linux Web サーバーを立てる。PC やスマートフォンから社内 Wi-Fi 経由でアクセス可能にする。
- **セキュリティ:** 外部インターネット公開は行わず、外部からは既存 VPN を利用する。新規外部回線は不要。
- **参考事例:** 次廣が別顧客向けに進めている VB + SQL Server 環境から Web ベースへ移行する案件と同様の考え方で進められる。

**確認待ち事項**

- **データベース定義書:** テーブル構造、キー項目、英字項目名と画面項目の対応関係。
- **サンプルPDF:** 注文書フォーマットの実例。機密情報はマスクまたは非公開扱いでよい。
- **DB書き込み権限:** ODBC 経由で書き込み設定が可能か、または別接続方式が必要か。
- **VBシステム保守体制:** 三菱関連会社への相談状況、既存システムの保守・改修方針。
