#### 話した内容（重要）

##### 1. 現状システムの概要

- **目的:** 出張買取の紙の売買契約書・明細書をデジタル化する。特定商取引法・古物営業法への対応と、現場の手間削減。
- **法的背景:**
  - 特定商取引法: 契約書の交付とクーリングオフ8日間の説明が義務。
  - 古物営業法: 帳簿の3年間保管。紙は引っ越し等で失いやすい。
- **主な機能:**
  - 商品写真を撮ると、Claude API で商品名を自動抽出。
  - 免許証写真から氏名・住所などを自動入力し、手書き誤記を減らす。
  - メルカリ相場を参照し、販売想定額・買取価格と当日の粗利見込みを出す。
  - 入力は GAS で Googleスプレッドシートへ自動連携。従業員別・日付別の集計。
  - 契約書は LINE で顧客へ送付。**LINE登録率 100%**、と当日。
- **インフラ:** Vercel でホスティング。コードは GitHub。
- **強み:** 渡邊さん自身が現場で使いながら作ったので、必要な機能が過不足なく、要件の質が高い。

##### 2. データ管理・アーキテクチャ

- **現状の問題:** スプレッドシートをデータベース代わりにしている。利用者が直接編集でき、数字欄への漢字入力などヒューマンエラーが起きやすい。
- **推奨:** 正規化した DB を持ち、スプレッドシートは裏側に隠す。入出力は Webアプリだけにする。
- **メリット:** データのコントロールがしやすい。見積書・請求書・分析レポートなど、出力形式を後から変えられる。
- **セキュリティ:** スプレッドシートは URL 共有で個人情報が漏れ得る。暗号化保存が必要。次廣は自システムで暗号化しており、サーバー侵害時にも本文が読めない状態にしている、と説明。
- **段階:** 利用者が少ないうちは GAS ベースでよい。運用費が確保できた段階、またはエラー対応が限界に達した段階で正式な DB へ移す。

##### 3. 運用保守の自動化

- 次廣の現行: エラー発生 → AI へメール通知 → ログ解析 → 修正提案を次廣へ → 承認後に本番反映。
- 渡邊さんの課題: 現場の買取と並行して保守できない。エラー対応を先に仕組み化する必要がある。
- **推奨:** 他者展開の前に、通知・修正・承認を自動化する。
- 既存事例: **木村 杏那**さんの Google Workspace 活用でも、スプレッドシート誤入力のエラー対応に苦労している、と紹介。

##### 4. API費用とコスト設計

- **現状:** Claude API で写真1枚あたり約5円。
- **問題:** 利用者が増えると API 費用が膨らむ。月額 **9,000円** では破綻しやすい。
- **案1（次廣）:** 利用者ごとに Claude の API キーを自己契約してもらい、費用を利用者負担にする。ITリテラシーの低い買取業者には難しい、という懸念も出た。
- **案2（渡邊）:** 上限枚数（例: 100枚）を置き、超過で停止＋追加課金の通知。
- **モデル分散:** Claude 依存は値上げで利幅が減る。OpenAI API や Gemini も選べる設計が望ましい。
- **料金:** 渡邊さんは月額 **30,000円** を検討。次廣の保守案件は月額 30,000〜145,000円程度で、何もしなくても入るストックになっている、と共有。

- **現状:** 全項目が1画面にあり、初めて使う人には複雑。
- **推奨:** 1画面1機能。案件作成 → 商品登録 → 顧客情報、のステップ。
- **初心者／熟練:** 最初は1点ずつ撮影。慣れたら一括アップロード。
- **バリデーション:** 半角・全角の自動変換など、入力制限をシステム側で持つ。
- **精度:** 複数枚（外装・型番）を一括すると同一商品が重複する。「スマホ」と「iPhone16」が別商品になる例。指示だけでは防げていない。1点ずつが確実。一括は熟練向けオプション。
