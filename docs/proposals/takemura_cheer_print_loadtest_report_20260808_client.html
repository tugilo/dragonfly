1. まず結論（30秒で読める版）

いまのままだと、イベントで本サイト（WordPress）に人が集中したとき、表示が大幅に遅くなるリスクが高いです。

対象わかりやすい結論判定
**告知用の入口ページ**（cheer--print.com）たくさんアクセスされても **余裕****問題なし**
**本サイト**（www.cheer-print.com）アクセスが増えると **数秒〜8秒超** かかることが多い**危険**

たとえ話にすると：

  • **入口（静的ページ）** … 受付カウンターが広く、並んでもすぐ通れる
  • **本サイト（WordPress）** … 奥の事務所が狭く、人が増えると一人ひとりの対応が極端に遅くなる

    • 「落ちてはいないが、使えないくらい遅い」 状態になりやすい、というのが今回の実測です。

    完全に表示できなかった割合はごくわずか（約0.07%）ですが、待ち時間が長すぎるため、来場者は「壊れている／繋がらない」と感じます。

    2. 今回何をしたか

    竹村様と合意した夜間枠で、実際のサイトへ 閲覧だけ のアクセスを段階的に増やし、どこから厳しくなるかを測りました。

    項目内容
    やり方「同時に何人かがページを見ている」状態を、弱い負荷から強い負荷へ段階的に増やす
    操作**見るだけ**（購入・ログイン・書き込みはしない）
    測った場所①告知用入口 ②本サイトの主要ページ（トップ／ニュース／購入方法／カテゴリ等）
    所要約28分（22:00開始 → 22:28終了）
    判定の目安**問題なし／要改善／危険** の3段階

    ※「仮想の同時閲覧数」は、会場の実人数と1対1ではありません。

    　ただし 「人が増えたときにサイトがどうなるか」 を数字で見るには十分です。

    3. 結果の見方（数字はここだけ覚えればOK）

    3-1. 告知用入口（静的）

    目安結果意味
    表示できた割合**100%**失敗なし
    遅い側の表示時間（目安）**約0.04秒**体感はほぼ一瞬
    判定**問題なし**告知URLとして十分強い

    対象: https://cheer--print.com/a-expo-fream/

    3-2. 本サイト（WordPress）

    目安結果意味
    表示できた割合**約99.9%**ほぼ落ちないが…
    真ん中の表示時間**約5.9秒**半数以上がこれ以上待つ
    遅い側の表示時間（目安）**約8.5秒**「固まっている」と感じる水準
    判定**危険**イベント集中時は機会損失リスク大

    対象例: https://www.cheer-print.com/ ほか主要ページ

    3-3. 一言で言うと

    入口は合格。本サイトはイベント耐性が不足。

    対策の主戦場は 本サイト側 です（制作会社さまの実装範囲）。

    4. なぜこうなるか（かんたん版）

    現状の本サイトは、ざっくり言うと 小さめのサーバー上で WordPress が毎回ページを組み立てる 構成です。

    人が少ない平常時は軽く見えます。

    しかしイベントで一気に増えると、

    1. アクセスのたびにサーバー内で処理が増える

    2. 待ち行列ができ、1人あたりの待ちが数秒に伸びる

    3. 画面は出るが「遅い」→ 離脱・クレーム・機会損失

    という流れになりやすいです。

    今回の数字は、その流れが すでに起き始めている ことを示しています。

    一方、告知用入口は あらかじめ用意した軽いページ なので、同じ強さの試験でも余裕がありました。

    「入口を静的に分ける」方針は正しい、という実測でもあります。

    5. 提案（具体的・優先順位つき）

    今回の成果として、「測った結果」＋「誰が・いつまでに・何をするか」 まで落とします。

    実装そのものは制作会社さま、窓口・意思決定は竹村様、測定・提案は次廣、という役割分担です。

    【最優先・今週中】制作会社さまへ依頼（必須3点）

    イベント本番（8/18）まで残り約 9日。次の3つを セット で進めてください。

    ① ページキャッシュを入れる（効果が一番大きい）

    項目内容
    **何を**よく見られるページを「あらかじめ作っておく」設定（ページキャッシュ）
    **なぜ**アクセスのたびに WordPress が重い処理をしなくてよくなる
    **どこまで**トップ・ニュース一覧・購入方法・カテゴリ・主要記事など、**公開の閲覧ページ**
    **注意**検索・ランダム表示・ログイン後画面などがある場合は除外ルールが必要 → **制作会社が設定**
    **完了の目安**「同じページを連続で開いても、サーバー負荷が上がりにくい」状態

    依頼文の例（そのまま転送可）:

    「負荷試験の結果、本サイトは集中時に応答が5〜8秒級になりました。イベント前に、公開ページ向けのページキャッシュ導入または強化をお願いします。対象はトップ・ニュース・購入方法・主要カテゴリです。」

    ② 画像・CSS・JS を CDN 経由にする

    項目内容
    **何を**画像やデザインファイルを、本サーバー以外（CDN）から配る
    **なぜ**本サーバーの仕事を減らし、表示の安定性を上げる
    **完了の目安**主要ページの画像が CDN 経由になっている（制作会社が確認）

    CloudFront 等、制作会社が扱いやすいもので構いません。

    「全部を完璧」より「まず画像と共通ファイル」 で効果が出ます。

    ③ イベント期間だけサーバーを一時的に大きくする

    項目内容
    **何を**いまの小さめサーバー（t3.micro 相当）を、**販売〜イベント前後だけ** 一段階以上アップ
    **なぜ**キャッシュ／CDN と併用すると安心材料になる。単体でも効くが、①②なしだと再び頭打ちしやすい
    **期間の例**販売開始〜イベント翌日まで（竹村様と制作会社で日程確定）
    **完了の目安**期間とスペック変更の実施日がカレンダーに入っていること

    【最優先・今日〜明日】竹村様側で決められること

    ④ 告知は必ず「静的入口」を先に出す

    項目内容
    **使うURL**https://cheer--print.com/a-expo-fream/
    **やめる／弱める**SNS・会場スクリーン・MCで **いきなり本サイトURLだけ** を一斉に出すこと
    **理由**入口は実測で余裕あり。本サイトへ同時殺到すると今回と同じ「遅い」が再現しやすい

    具体的な当日オペレーション例:

    1. 会場・SNSの一次案内は 静的入口のみ

    2. 入口で内容を見せ、必要な人だけ本サイト／フレーム作成へ進む

    3. MCで「今すぐアクセス！」と言う場合も、入口URL を出す

    4. 可能なら、案内を 数分ずらす（一斉より波状の方が安全）

    ⑤ 制作会社へ「期限つき」で依頼する

    依頼希望期限（案）
    ①ページキャッシュ**8/11（火）まで** に一次反映
    ②CDN**8/13（木）まで**

    監視の見える化イベント当日、異常時に誰が見るか（担当者名・連絡手段）

    【推奨】対策後の短い再確認（次廣）

    ①〜③の反映後、強い負荷をもう一度かけず、短時間の再測定で「改善したか」を確認できます。

    残スコープ内で対応可能です。希望があれば日程を合わせます。
