## 1. 結論

作る Web は1つ。人が使う機能は **2つ**。基幹（VB + Oracle）には手を入れません。

| 機能 | 一文 |
|------|------|
| **1. 注文入力** | 注文書PDF をまとめて上げる → 項目ごとの欄に抜き出す → 人が1件ずつ直して承認 → **CSV に出す** → 既存システム側の取込プログラムが Oracle に入れる |
| **2. 製本作業予定表** | いま Excel を印刷してペンで組んでいる週次の予定表を、同じ並びの画面にする。手で置く操作に加えて **自動配置**。**ルールが納期・稼働枠などの制約を守り、AI が順番の案と理由を出し、人が確定する** |

**第4回（10/5）で決まったこと（変わらず）**

1. **Oracle へ直接書き込まない。** こちらの DB に仮登録 → CSV 出力 → 既存システムの取込プログラムで Oracle へ。
2. **人が必ず確定する。** 注文は1件ずつ承認。予定表は人が確定するまで変わらない。
3. **メール添付の生産依頼表（Excel）は、まず手で入力する画面から。**

**v3 からの変更（10/14 のご意向を受けて）**

- 自動配置を「ルールのみ。AI は将来」から **「ルール＋AI＋人」の三層（§4.2）** に変更し、AI 連携を必須に含めた（旧 O4 ¥250,000 を必須へ移動。必須合計 ¥2,900,000・概算）。

## 3. 機能1 — 注文入力

### 3.1 流れ

```text
[注文書PDF（メール添付）]
  → まとめてドラッグ＆ドロップ
  → 1件ずつ解析し、項目の欄に抜き出す
  → 人が欄を直す（必ず人が見る）
  → 「承認」で補助DBに登録（仮番号）
  → 「次へ」で次のPDFの解析が始まる
  → 承認済みを CSV に出力（既定フォルダ）
  → 既存システムの取込プログラムが Oracle へ（手動実行・既存システム側）
```

### 3.2 対象と、PDF の読み方（要確認）

- 最初は **型の揃った主要1社** の PDF。他社フォーマットは後から足す
- **解析方式は「PDF のテキスト層を読む」が前提**（AI ではない）。これが M2 の見積範囲
- **ただし、受領済みのサンプル（注文書.pdf）は複合機でスキャンした画像のみで、テキスト層がありません。** 実際にメール添付で届く PDF にテキスト層があるかを **最優先で確認**します（数件のご提供をお願いします）
- 画像のみの PDF が主流なら、方式を **社内 OCR** か **帳票読取 AI（原本を外部に送る。送信情報・契約条件・費用を配置用 AI とは分けて整理）** のどちらかにし、精度検証と費用を **別途**提示します。専門家資料の「PDF を AI で読み取る」はこの別方式に当たり、現時点の必須範囲には含みません
- PDF 以外の注文（メール添付の生産依頼表 Excel）は **手動入力画面**で同じ補助DBに登録 → 同じ CSV へ

### 3.3 やらないこと

- 100%自動登録。人が1件ずつ承認する
- Oracle への直接書き込み。Oracle にテーブルも足さない
- 手書き注文書の OCR

## 4. 機能2 — 製本作業予定表

### 4.1 画面

- 縦に日付（週）、横に作業場所（板橋1F／1F予備／2F／2F予備／ふじみ野／ふじみ野予備）
- 左に **未配置**（機能1で承認した注文、手動入力した生産依頼表）
- 未配置から日付×場所のマスへドラッグ。先頭・間・末尾の差し込み位置を出す
- カードに **作業時間** を入れる（最初は0。入れると橙→緑）。マス・日・週の合計を出す
- 印刷に無い注文の手追加、枠の塞ぎ、入れ替え

### 4.2 自動配置 — ルール・AI・人の三層

| 層 | 役割 | 決定済み／未確定 |
|----|------|------------------|
| **ルール（制約・検証）** | 納期・作業場所の稼働枠・判型×仕様の設備適性・優先度で「置けるか」を決め、候補を絞る。AI の案を **検証**し、制約違反は採用しない。AI が止まったときは **ルールだけで提案**する | 枠組みは決定。条件の実値（稼働枠・適性・優先度）は担当者ヒアリングで確定（未） |
| **AI（提案・説明・指示の支援）** | ①ルールが絞った候補に対し、**順番の案と理由（日本語）** を返す ②担当者の **言葉での指示**（「A社の分を来週に前倒し」「木曜の2Fを空ける」など **定型の操作**）を受けて変更案を出す。**曖昧な指示は確認を返し、勝手に実行しない** | ①は必須に含める（決定）。②の **範囲（定型に限るか、自由度の高い指示まで含めるか）は未確定**（見積 v4 §5.1）。AI サービスは未選定 |
| **人（確定）** | 画面で動かして確定。AI 案はカードの色で区別。動かした内容と理由を記録 | 決定（第4回） |

**修正履歴の使い方（混同しないために）**

- 人が直した内容は記録し、**直近の修正例を次回の提案時に「参考例」として AI に渡す**。これにより、担当者の好み（この得意先は前倒し気味に、など）が案に反映されやすくなる
- これは **独自モデルの学習でも、重みの自動最適化でもない**。履歴がたまるだけで精度が自動的に上がる仕組みではなく、月次で修正傾向を見てルールと指示文を人が見直す
- 専門家資料の「過去の実績から学習する」「直した結果を反映して精度を上げていく」は、この「参考例の参照＋人による見直し」と読み替えてください

**AI が止まったとき**

- タイムアウト・エラー・不正な応答・API 停止のときは、**ルールだけの提案に自動で切り替わり**、画面にその旨を出す。従来の手組みにもいつでも戻れる

### 4.3 やらないこと

- 予定表の CSV 出力・印刷機能（第4回決定。データ引渡し用の取出し機能は別。基本設計 §2）
- 順番の自動確定
- 独自モデルの学習、重みの自動最適化
- 実作業の開始・終了や実績工数の自動収集（未定義。任意 O3 の前提として別途検討）
- 過去の予定・実績データの大量整備・移行（必要なら別途）

## 5. つながりと置き場所

```text
[ブラウザ（社内）]
    ↓
[Web アプリ（Docker・社内）]  ← 機能1・機能2・ユーザー・ログ
    ↓ 補助DB（MariaDB）に仮登録・証跡・予定表
    ↓ CSV 出力（既定フォルダ・ファイル名は一意）
[取込プログラム（既存システム開発会社）]  ← 手動実行
    ↓
[Oracle（受注の正・既存）]  ← VB もこれまでどおり

[Web アプリ] → 外向き HTTPS（1宛先）→ [AI API（国宝社様名義）]
    ※ 送るのは配置に要る最小限の項目を ID 化したもの。原本・氏名・金額は送らない（§7）
```

- 置き場所は **社内**。既存 Windows の Hyper-V 上 Ubuntu、または **専用PC（16GB・SSD）** のどちらか。外からの受け付けは無い。Google Workspace / GAS は使わない
- **外向きの通信は AI API への 1 宛先のみ**。ここが v3 からの唯一の変更点
- 補助DB は **正にしない**。受注・得意先・注文番号の正は Oracle のまま
- 詳しくは [システム構成図 v4](kimura_kokuhosha_system_architecture_v4_20261026.md)

## 7. AI に渡す情報と守り方（設計方針。実装・検証はこれから）

| 項目 | 方針 |
|------|------|
| 送る情報 | **許可リストで限定。** 注文ID・判型・数量・納期・予定工数・優先度・作業場所の空き状況・直近の修正例（ID 化） |
| 送らない情報 | 氏名・住所・連絡先・金額・書名・PDF 原本。得意先名は ID に置き換え、対応表は社内に保持 |
| 自由記述 | 備考・修正理由・言葉での指示は送信前に変換・除去。判別できない場合は **送信を止めて確認** |
| 言い切らないこと | ID 化しても数量・納期などは業務情報。**完全匿名・漏えいリスクゼロとは言わない** |
| 通信・鍵 | 承認した送信先への HTTPS のみ。API キーはサーバー側で暗号化保管し、画面・ソース・通常ログに出さない。最小権限。失効・再発行手順を定める |
| AI の権限 | AI に DB 接続・任意ファイル参照・更新実行の権限を直接与えない。社内アプリが選んだ情報だけを渡す |
| 出力の扱い | 所定形式・実在 ID・業務制約で検証。人が確定するまで反映しない |
| ログ | 送信ログ（日時・実行者・送信項目・結果・モデル版）を残す。生の機密情報・キーは記録しない。例外ログ・バックアップも同じ |
| 異常時 | 通信停止 → キー失効 → 影響確認 → 国宝社様へ連絡 → ルール運用へ切替 |
| サービスの条件 | **「学習に使われない」と「保存されない」は別。** OpenAI API は公式ページ（2026-10-26 確認）で、入力は既定で学習に使われない／不正利用監視ログは最長 30 日保持／保持なし（Zero Data Retention）は事前承認制／処理地域の指定は別途適格性確認。他社 API は同じ条件と見なさず、選定時に個別確認する |

## 8. 運営保守の体制

- **tugilo は、AI と管理の仕組みを組み合わせ、特定の個人に依存せず管理・引継ぎができるように構築しています。次廣に何かあっても、別の担当者が管理を継続できる体制とします。**
- 本件でも、設計書・ソース・Docker 構成・設定・DB 定義に加え、起動・更新・確認・バックアップ・復旧の手順、連絡経路、必要なアクセス権・認証情報・AI 利用環境（国宝社様名義のアカウント）の引継ぎ方法を整理して納品します
- 通常の窓口は次廣。対応の目安（一次回答・暫定対処の日数）は、受付時間・休日・保守契約の有無と合わせて契約時に定めます。**復旧時間の保証や 24 時間対応はお約束しません**
- 止まったときは従来の手入力・手組みに戻れます。AI だけが止まったときはルール提案に戻ります
- 瑕疵対応の期間・範囲、プログラムの権利（譲渡か利用許諾か）は契約で定めます（本書では決めません）

| 「年内に開発に着手」「10月契約・11/2 着手（v3）」 | 過去の計画。発注可能時期を起点に再調整 | スケジュール v4 |
| 「利用する AI のサービスは開発会社と確認中」「OpenAI 等を想定（窓口相談時は Gemini）」 | 未選定。申請書類での記載との整合を取ってから選定 | 専門家に確認 |

## 13. 確認したいこと

**国宝社様（木村様）へ**

1. 実際にメール添付で届く注文書 PDF を数件（テキスト層の有無を確認するため）
2. AI にどこまでさせたいか（順番の案と理由まで／定型の言葉での指示まで／自由度の高い指示まで）
3. 「データ投入2割」で想定していたもの（過去の予定・実績データか、得意先マスタか）
4. AI API の契約名義を国宝社様にする場合のアカウント作成・支払いの段取り。申請書類で AI をどう書いているか
5. 置き場所（既存 Hyper-V か専用PC か）。予定表 Excel の実ファイル。担当者ヒアリングの日程
6. 保守契約を結ぶか

**専門家（花村様）・公社へ**

1. 助成の上限・助成率・対象経費（AI 連携の構築・検証費の扱い、サーバー構築費、API 利用料）
2. 交付決定前の着手・契約の可否と、発注可能時期の見込み
3. 見積・請求書・納品物・選定理由書に求められる形式と粒度
4. 申請書類における AI の記載（PDF 読取・学習）と、本提案（§12）の読み替えが問題ないか

**既存システム開発会社へ**

1. CSV レイアウト（項目・順・型・文字コード・改行）の提示時期
2. 約100万円の範囲（レイアウト設計、取込プログラム、Oracle 側改修）
3. 取込結果の通知方法、UPDATE／DELETE の扱い、再取込時の重複防止、得意先コードの照合、取込口の完成時期
