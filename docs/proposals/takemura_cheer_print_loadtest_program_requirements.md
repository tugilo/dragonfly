## 1. 目的

**ローカル Docker（推奨）** から Cheer Print 関連サイトへ段階的な HTTPS 負荷をかけ、画面上で進捗を見ながら測定し、終了後に日本語報告書を自動生成する。

1. 静的入口（告知URL）が想定アクセスに耐えられるか  
2. WordPress 本サイトがどこから遅くなるか／落ちるか  
3. ボトルネック候補（応答悪化の傾向）を示す  
4. **試験終了後に、誰が見ても分かる日本語の報告書を自動生成する**  

本プログラムは **測定＋自動報告**。本番 AWS／WordPress の設定変更は行わない。

### 1.1 なぜローカル Docker を第一候補にするか

| 観点 | ローカル Docker | tugilo.com（さくらのVPS）から実行 |
|------|-----------------|-----------------------------------|
| tugilo.com の負荷 | **載せない** | CPU／回線を消費し、他サービスに影響しうる |
| 監視しながら報告 | **コンソールを見ながら実施しやすい** | SSH 越しで見づらい |
| 測定の歪み | 発生側と対象が分離 | 発生側 VPS が先に詰まる可能性 |
| 再現性 | `grafana/k6` イメージで揃う | 同様に可能だが常用は不要 |
| 注意 | 自宅回線の上りが弱いと VU 上限が制限される | 回線が強い場合の予備 |

**方針:** 明日の本番枠も **ローカル Docker から実行**する。VPS は回線不足で測れないときだけの予備。

## 3. 機能要件

### FR-1. 段階負荷（Stage A / B / C）

| Stage | 目的 | VU 目安（パラメータ化） | 時間目安 |
|-------|------|-------------------------|----------|
| A | スモーク（壊さない確認） | 10〜20 | 1〜3 分（枠内では 10〜15 分バッファ含む） |
| B | ランプアップ（限界感） | 20→50→100→合意上限 | 20〜30 分 |
| C | ピーク維持 | 合意上限を 5〜10 分 | 15〜20 分 |

- VU・各 stage の duration・上限は **環境変数または CLI 引数**で変更できること  
- デフォルトは安全寄り（低い VU）。本番枠では合意値に上げる  

### FR-2. シナリオ分離（静的入口 / WP 本サイト）

最低 2 系統を用意する（同時実行または連続実行）。

| シナリオ ID | 対象 | 目的 |
|-------------|------|------|
| `static_landing` | `https://cheer--print.com/a-expo-fream/` 中心 | 告知入口の耐性 |
| `wp_origin` | `https://www.cheer-print.com/` 配下の主要ページ | WP／EC2 オリジンの耐性 |

WP 側のページ候補（重み付け・パラメータ化）:

| 優先 | URL |
|------|-----|
| 必須 | `/` |
| 必須 | `/news/` |
| 必須 | `/how-to-purchase/` |
| 中 | `/bl/` `/sports/` `/entertainment/` |
| 任意 | イベント連動記事（確定後に追加） |

### FR-3. HTTP 挙動

- メソッド: **GET のみ**  
- User-Agent: 識別可能な固定文字列（例: `cheer-print-loadtest/1.0 (authorized; tugilo-sakura-vps)`）  
- タイムアウト: 設定可能（既定例 30 秒）  
- `sleep`（閲覧間隔）を設定可能。同じ VU でも RPS が変わることをコメントで明示  

### FR-4. 計測・出力

記録・表示する指標:

| 指標 | 必須 |
|------|------|
| HTTP 成功率 | 必須 |
| エラー率（非 2xx／失敗） | 必須 |
| 応答時間 p95（および可能なら p50 / p99） | 必須 |
| 到達 VU / 実行時間 | 必須 |
| RPS（概算） | 推奨 |
| ステータスコード分布 | 推奨 |
| シナリオ別の内訳 | 推奨 |

出力:

- コンソールサマリ（実施中／終了時）  
- 結果ファイル（JSON またはテキスト）を **ローカル `results/`** に保存できること  
- **自動生成の日本語報告書**（FR-7）  

### FR-5. 安全装置

| 機能 | 内容 |
|------|------|
| 最大 VU 上限 | 設定値を超えない |
| 即停止 | Ctrl+C／プロセス kill で安全に止まる |
| abort 条件（推奨） | エラー率が閾値超過、または連続失敗で自動停止（実装可能な範囲） |
| 禁止対象のガード | コード上、wp-admin／login／contact POST／検索爆撃 URL をデフォルトに含めない |

### FR-6. 実行手順ドキュメント

次が分かる README を同梱する。

1. **ローカル（Docker）**でのドライラン／本番相当実行  
2. **さくらのVPS（`ssh tugilo.com`）**での実行（任意・本番候補）  
3. 依存（Docker／node）。**Mac への k6 直入れは必須としない**  
4. 結果ファイル・報告書ファイルの場所  
5. 停止方法  

### FR-7. 自動報告書（誰が見ても分かる形式）

試験終了後（または Stage／シナリオ単位の終了後）に、**人が読んで理解できる報告書を自動生成**する。  
手書きの再集計を前提にしない。

#### 出力形式

| 形式 | 必須 | 用途 |
|------|------|------|
| **Markdown（.md）** | 必須 | リポジトリ／Messenger／メールに貼れる |
| HTML（.html） | 推奨 | ブラウザでそのまま開いて見せられる |
| 生 JSON | 必須 | 再処理・監査用 |

ファイル名例: `results/report_YYYYMMDD_HHMM_JST.md`

#### 読み手

- 竹村さん（非エンジニアでも分かる）  
- 制作会社（次アクションが分かる）  
- 次廣（数値根拠が残る）  

#### 報告書に必ず含める章

| # | 章 | 内容（平易な言葉） |
|---|-----|-------------------|
| 1 | 結論（一番上） | **問題なし／要改善／危険** の総合判定＋一言理由 |
| 2 | いつ・何をしたか | 実施日時（JST）、発生元（ローカル Docker 等）、対象URL、最大VU、所要時間 |
| 3 | シナリオ別の結果 | 静的入口／WP本サイトを分けた表（成功率・遅さ・判定） |
| 4 | どこから厳しくなったか | Stage B で遅くなり始めた目安（分かる範囲） |
| 5 | 数字の詳細 | p50/p95/p99、エラー率、RPS、ステータス分布（折りたたみ可／後半に配置） |
| 6 | 次にやるとよいこと | キャッシュ／CDN／一時スペック等の **優先順位付き提案候補**（自動テンプレ＋数値に応じた文言） |
| 7 | 注意書き | 「保証ではない」「VU≠実人数」「本番監視は制作会社」など |

#### 判定ルール（自動）

数値はパラメータ化可能。デフォルトたたき台:

| 判定 | 条件（例） |
|------|------------|
| **問題なし** | 成功率 ≥ 99% かつ p95 ≤ 2.0s |
| **要改善** | 成功率 95〜99% または p95 が 2〜5s |
| **危険** | 成功率 < 95% または p95 > 5s またはタイムアウト／接続失敗が継続 |

- 総合判定は、シナリオのうち **最も悪い判定** を採用（静的が問題なしでも WP が危険なら総合は危険）  
- 判定根拠の数値を同じ段落に併記する  

#### 文体・見せ方

- 専門用語は使う場合に一言説明（例: 「p95＝遅い側の目安」）  
- 絵文字や装飾に頼らず、見出しと表で構造化する  
- 「サーバーが壊れた」など誤解を招く表現は使わない  
- 竹村さんがそのまま制作会社へ転送できる完成度を目指す  

#### 生成タイミング

1. 各シナリオ終了時に部分レポート（任意）  
2. **全試験完了後に統合レポート（必須）**  
3. 実行ラッパ（`run.sh` 等）からワンコマンドで「試験→報告生成」まで流せるのが望ましい

## 5. 非スコープ（やらないこと）

- wp-admin／ログイン／フォーム送信／検索爆撃／XML-RPC／API 連打  
- Cheer Print EC2 上での負荷発生  
- AWS／WP／CDN の本番設定変更  
- Religo（www/）への機能追加  
- 無停止保証・制作会社の監視代行  
- k6 browser の大量 VU

## 6. 合否判定（自動報告書に反映）

プログラムは数値に基づき **問題なし／要改善／危険** を自動付与する。  
最終的なビジネス判断（対策を入れる／様子見）は人が行うが、**報告書の結論欄は自動で埋める**。

| 判定 | 意味（一般向け） |
|------|------------------|
| **問題なし** | 想定した試験条件では、ほぼ問題なく表示できる |
| **要改善** | 表示はできるが、遅くなる時間帯がある |
| **危険** | エラーや表示不能の可能性が高い |

数値たたき台: 成功率 ≥99%／p95 ≤2s など（FR-7）。実施時の合意で閾値変更可。

3. Stage A→B→C 相当の stages がパラメータで動く  
4. p95・エラー率・成功率が取得できる  
5. 禁止 URL がデフォルトシナリオに含まれない  
6. README で **Docker ローカル**と **VPS** の両方の手順が分かる  
7. **試験後に日本語の自動報告書（Markdown）が生成され、結論判定が一目で分かる**  
8. 報告書サンプル（ドライラン結果）を WORKLOG または `tools/.../samples/` に残せる
