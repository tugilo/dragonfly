## 2. 原則

1. **基幹は触らない。** 受注・得意先・注文番号の正は Oracle。補助DB は正にしない
2. **人が必ず見る。** PDF 解析結果は人が1件ずつ直して承認。承認前は CSV に出ない
3. **CSV が境界。** Oracle へは開発会社の取込プログラムだけが書く
4. **自動配置は提案。** ルールの案も AI の案も、人が確定するまで予定表に反映しない
5. **段階的に自動化。** 生産依頼表 Excel は手動入力から。読込・メール取込は後から
6. **出さない。** 予定表の印刷・CSV 出力は作らない
7. **AI は制約の内側で動く。** ルールが候補を絞り、AI の案をルールが検証する。AI が止まればルールだけで提案する
8. **外に出す情報は最小限・ID 化・記録。** 許可リストにある項目だけを送り、原本・氏名・金額は送らない。送った内容はログに残す
9. **データは国宝社様のもの。** 補助DB の全データはダンプ・CSV で取り出せるようにする（運用のための印刷・CSV 機能とは別）

## 6. CSV 連携 方式（変更なし・確認事項を追加）

### 6.1 決まっていること（開発会社資料 2026-09-29）

| 項目 | 内容 |
|------|------|
| 形式 | CSV 等のテキスト |
| レイアウト | **開発会社が設計・提示**（未受領） |
| タイミング | 手動実行。既定フォルダに置いて取込プログラムを起動 |

### 6.2 tugilo 側の設計

| 項目 | 設計 |
|------|------|
| ファイル名 | `ORDER_YYYYMMDD_HHMMSS_NNN.csv`。常に新規。再出力も新しい名前 |
| 文字コード・改行 | 開発会社提示に従う（候補: Shift_JIS／CRLF） |
| 1ファイルの単位 | 事務が選んだ承認済み draft（既定は「未出力の承認済み全部」） |
| 控え | 同じ内容をサーバー内に保存。export_batches に記録 |
| 出力後 | draft を exported に。取込結果が戻れば imported／import_error |
| 項目 | 生産依頼表の項目を基本に、受注ヘッダー／明細の必須列へ対応。対応表は仕様書 §5 |

### 6.3 開発会社への確認事項と tugilo 案

| 確認事項 | tugilo 案 | 代替 |
|----------|-----------|------|
| 取込結果の通知方法 | 結果ファイル（同名 + `_result.csv`）を既定フォルダに書く。Web が読んで draft に反映 | VB 画面で見るだけにし、Web は exported 止まり |

## 7. 自動配置 — ルール層・AI 連携・人の確定

### 7.1 三層の分担

| 層 | 入力 | 処理 | 出力 | 決定済み／未確定 |
|----|------|------|------|------------------|
| **ルール層（F-09）** | 対象週、未配置・配置済みカード（固定可）、稼働枠、納期（決定日 > 配本日 > 希望日）、作業時間、優先度、設備適性 | 制約で候補日・候補場所を絞る。ルールだけの並べ方（納期順 → 優先度 → 空き）も作る。AI 案を検証（形式・実在 ID・件数・納期・稼働枠・適性）。AI 不可時の切替 | 候補集合、ルール案、検証結果 | 枠組みは決定。**条件の実値は担当者ヒアリングで確定（未）** |
| **AI 連携（F-15／F-17／F-18／F-19）** | ルール層の候補（ID 化・許可リスト済み）、業務ルールのプロンプト、直近の修正例（件数・期間は設定） | 順番案と理由（日本語）を所定形式で返す。言葉での指示（定型範囲）を変更案に変換。曖昧なら確認文を返す | 案・理由・確認文 | ①案・理由は決定。**②言葉での指示の範囲は未確定**（定型に限るか）。**サービス未選定** |
| **人（S-06／S-07）** | ルール案・AI 案（色で区別）・理由・検証結果 | 確認・修正・確定。採否とカードの移動を記録 | 確定した予定表 | 決定（第4回） |

### 7.2 流れ

1. 予定組み担当が「自動配置」を押す、または言葉で指示する
2. ルール層が候補を絞る。候補が無いカードは「入らない」として理由付きで出す
3. 送信制御が候補を ID 化し、許可リストの項目だけを並べる。判別できない自由記述があれば **送信を止めて確認**
4. AI API を呼ぶ（モデル固定・タイムアウト）。送信ログを記録
5. 返答をルール層が検証。違反カードは不採用にし理由を表示。**応答なし・不正応答なら ルール案に切替**し、画面に表示
6. S-07 で現在と案を並べ、人が確定。確定まで予定表は変わらない
7. 確定後の人の移動（1週間以内）を修正履歴に記録。月1回「提案どおり／人が直した」の割合を出す

### 7.3 修正履歴の扱い（学習ではない）

- 記録する: 提案（rule／ai）、採否、人の移動、理由、確定者
- 使う: **直近 N 件（設定。既定 20 件・4 週）の修正例を、次回提案時に「参考例」としてプロンプトに含める**（ID 化済み）
- しない: 独自モデルの学習、重みの自動更新、過去全データの投入。**履歴がたまるだけで精度が自動的に上がるとは言わない**
- 月次で修正傾向を見て、管理者がルール（稼働枠・適性・優先度の重み）と業務ルールのプロンプトを見直す

### 7.4 AI 設定・版管理（F-19）

| 項目 | 設計 |
|------|------|
| モデル | モデル名を設定で固定。自動で新版に変わらない。変更時は過去4週程度の確認用データで再評価してから切替（**同一モデルでも同一結果は保証しない**） |
| プロンプト | システム部分（形式・禁止事項）は tugilo が管理。**業務ルール部分**（「納期優先」「同一判型はまとめる」等）は管理者が S-08 で編集。prompt_versions に版・変更者を記録 |
| 記録 | auto_plan_runs に rule_version／prompt_version／model_name／ai_used／fallback_reason |
| 送信先 | 承認した 1 宛先を設定。変更は管理者のみ・ログに残す |

## 7A. AI 送信時のセキュリティ設計方針（実装・検証予定。実装済み・検証済みではない）

| # | 観点 | 設計方針 |
|---|------|----------|
| 1 | 送信項目の限定 | **許可リスト**で限定。注文ID（alias）・判型・数量・納期・予定工数・優先度・空き状況・直近の修正例（alias 化）だけを送る。リストに無い項目はコード上で送れない構造にする |
| 2 | ID 化 | 得意先名・書名・担当者名は entity_aliases で ID に置換。対応表は社内 DB のみ。受け取った案を社内で元の名前に戻して表示 |
| 3 | 送らない情報 | 氏名・住所・連絡先・金額・書名・PDF 原本・自由記述の原文。配置用 API に送信しない |
| 4 | 自由記述・指示文 | 備考・修正理由・言葉での指示は、送信前に **定型の構造（操作種別・対象 alias・日付・場所）に変換**し、原文は送らない。変換できない（判別できない）場合は **送信を止めて担当者に確認** |
| 5 | 言い切らない | ID 化後も数量・納期・工数は業務情報。**完全匿名・漏えいリスクゼロとは表現しない**。送信範囲・履歴件数・保存期間は国宝社様と合意する |
| 6 | 通信 | 承認した送信先への HTTPS のみ（証明書検証）。FW で外向き宛先を限定。社内から外への 1 経路 |
| 7 | 鍵 | API キーはサーバー側で暗号化保管。画面・ソース・通常ログ・バックアップに出さない。最小権限（配置用プロジェクトに限定）。**失効・再発行の手順**を運用手順書に書く |
| 8 | AI の権限 | AI に DB 接続・任意ファイル参照・外部検索・更新実行の権限を直接与えない。社内アプリが選別した情報だけを渡す。注文の文字列や指示文を「ルール・権限を変える指示」として採用しない |
| 9 | 出力の検証 | 所定形式・実在 alias・件数・納期・稼働枠・設備適性で検証。違反は不採用。**人の確定前に反映しない** |
| 10 | ログ | 送信ログに日時・実行者・送信項目名・件数・結果・モデル版・応答時間。**本文・キー・生の名称は残さない**。例外ログ・バックアップも同じ方針。閲覧は管理者のみ・保持期間を定める |
| 11 | 異常時 | 誤送信・鍵漏えいの疑い・サービス側の障害のとき: **通信停止 → キー失効・再発行 → 送信ログで影響確認 → 国宝社様へ連絡 → ルール運用へ切替**。手順書と連絡経路を定める |
| 12 | サービス条件の確認 | **「学習不使用」と「保存なし」を区別する。** 選定サービスの公式条件で、学習利用・監視ログ・応答保存・ファイル・キャッシュ・処理地域・削除条件を確認し、国宝社様の承認後に利用する |
| 13 | 導入前検証 | 実際の送信内容（ログと送信直前のペイロード）、権限、ログの中身、異常時停止・切替を **並行テスト前に検証**し、記録を納品する |
| 14 | 帳票読取 AI を足す場合 | 原本送信を伴うため、配置用 AI とは **別経路・別契約条件・別費用**として再整理する。本方針の対象外 |

**OpenAI API の公式条件（2026-10-26 に https://developers.openai.com/api/docs/guides/your-data を確認）**

- API に送ったデータは、明示的にオプトインしない限り **モデルの学習に使われない**
- **不正利用監視ログ**は既定で全 API 利用について生成され、**最長 30 日**保持（法令等で延長あり）
- **Zero Data Retention（保持なし）／Modified Abuse Monitoring は事前承認制**で、追加要件の承諾が要る。承認なしでは「保存なし」は保証されない
- Responses API は `store` 既定で応答を 30 日保持。`store=false` で保持なし（ZDR 組織では常に false 扱い）
- プロンプトキャッシュは暗号化された状態で GPU ローカルに最長 24 時間
- データレジデンシー（処理地域の指定）は営業窓口での適格性確認が要り、対象モデルは 10% 上乗せ。米国以外の地域は監視制御の承認と契約修正が要る
- **Anthropic・Google は未確認。** 同一条件と見なさず、選定時に個別確認する

## 13. 運営保守の継続体制（次廣確認 2026-10-26）

- **tugilo は、AI による管理・対応支援と、運営保守の手順を仕組み化した構成を組み合わせ、特定の担当者に依存せず管理・引継ぎができるように構築している。次廣に何かあっても、別の担当者が管理を継続できる体制とする。**
- 本件で引き継げるようにするもの: 設計書・ソース・環境構成・設定情報（鍵は別経路）、起動・更新・確認・バックアップ・復旧の手順、連絡経路、必要なアクセス権（サーバー・DB・FW・共有フォルダ）、認証情報の受け渡し方法、AI 利用環境（国宝社様名義のアカウント・キーの所在・失効再発行）
- 通常の窓口は次廣。対応の目安（一次回答・暫定対処の日数）は受付時間・休日・保守契約の有無と合わせて契約で定める
- **書かないこと:** 協力者の氏名（未確認）、24 時間対応、復旧時間の保証、著作権の譲渡、無償修正期間の日数（いずれも契約で定める・次廣判断）
